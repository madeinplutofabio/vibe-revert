# Windows `.cmd` mediation — lifecycle verification runbook

- Milestone: H11.1 (dogfood findings/fixes); pairs with
  [ADR 0005](../adr/0005-windows-command-resolution-and-launch.md).
- Scope: how the **interactive** lifecycle behavior of the bounded `.cmd`
  command-line mediation is verified on a real Windows console, and what evidence
  is retained.
- **Status (2026-08-04): Decision 7 OPEN.** Stage A `windows-cmd-bounded-v1` is formally
  ineligible (all four required hosts prompted and required forced recovery). A separate,
  disposable **native control-router feasibility spike** then succeeded on one host for a
  `.cmd → native descendant` launcher topology (real Ctrl+C reached the native child while
  `cmd.exe`'s batch prompt was suppressed by a debugger). That spike is **not** attested Stage A
  evidence and **not** product support; productionization is deferred to post-beta. The shipped
  Windows contract is unchanged: native executables are direct-spawned, interactive `.cmd` is
  gated. See **Recorded results** at the end of this document.

## Why this is manual

The bounded `cmd.exe` command-line mediation — argument transport, stdout/stderr,
and exit codes — is validated automatically by the Windows live spike. **Lifecycle
behavior — whether a real keyboard Ctrl+C reaches the agent and whether `cmd.exe`
then completes cleanly — cannot be faithfully generated by automated Vitest.** A
synthesized console control event does not exercise the same console conditions as
a human keypress and must not be represented as equivalent. This runbook records
the interactive verification and the evidence retained for it.

## Result vocabulary

Lifecycle is recorded as four separately-named results. **This runbook fills the
first two (manual);** the automated spike
(`packages/cli-commands/test/command-launcher-lifecycle-live.test.ts`) fills the
last two.

```yaml
interactive_delivery:          # manual (this runbook)
  - received
  - not_received
  - indeterminate

wrapper_completion:            # manual (this runbook)

  - batch_prompt_then_exit
  - batch_prompt_hang
  - wrapper_hang_without_prompt
  - indeterminate

  - tree_stopped_sentinel_survived
  - tree_not_fully_stopped
  - sentinel_affected
  - indeterminate

  - descendants_terminated_with_wrapper
  - mixed_descendant_state
  - indeterminate
```

## Eligibility rule

Interactive `.cmd` mediation is eligible for production wiring in `run` only when:

- `interactive_delivery: received`
- `wrapper_completion: clean_exit`

Any other outcome — including `batch_prompt_then_exit`, `batch_prompt_hang`,
`wrapper_hang_without_prompt`, and `indeterminate` — is **blocked by default**.
Accepting another `wrapper_completion` outcome requires an explicit **ADR 0005
amendment** that defines the resulting interaction and cleanup contract; it is not
a per-run waiver. In particular, requiring the user to answer
`Terminate batch job (Y/N)?` is not accepted product behavior for `viberevert run`
absent such an amendment.

When blocked: native-executable resolution is preferred (modern Claude Code is
covered through its native executable), and `.cmd`-only agents receive an accurate
actionable error until an explicit Windows lifecycle-ownership mechanism exists.
Forced recovery is emergency behavior, never the interactive path.

## Two-stage verification

**Stage A — lifecycle eligibility (this runbook's primary purpose).** A dedicated
H11.1 inherited-console harness, independent of any `run` production wiring. It
establishes only the interactive lifecycle fields. Fields that require a VibeRevert
session are `not_applicable` in Stage A.

**Stage B — CLI integration regression.** Only after Stage A is `eligible` and
H11.2 `.cmd` wiring exists: a separate run through the real `viberevert run` CLI
confirming integration did not change the result, and recording the session-level
fields. Do not use H11.2 production wiring for the initial eligibility decision (it
is blocked until Stage A passes).

## Fixture

An interactive agent fixture that makes delivery and exit observable — a `.cmd`
shim forwarding (via the resolved `process.execPath`) to a Node script that:

- writes a readiness record `{ pid, token, ts }` and prints `AGENT-READY`;
- rewrites a heartbeat record `{ pid, token, seq, ts }` at a fixed interval;
- installs a `SIGINT` handler that writes a finalization record
  `{ pid, token, sigint_ts, exit_intent: 130 }`, prints `AGENT-INTERRUPTED`,
  stops the heartbeat and exits with intent `130`;
- otherwise remains alive.

Repository-local and temporary: no network, no real agent, no product-state
mutation and no persistence outside the dedicated evidence directory. The `token`
is unique per invocation and binds every record and PID to this exact run.

## Stage A harness

The harness builds and spawns the SAME validated plan the product would, with the
candidate production options:

- `buildCommandLaunchPlan(...)` producing `windows-cmd-bounded-v1`;
- spawn the returned plan with `shell: false`, `windowsVerbatimArguments: true`,
  **inherited** stdin/stdout/stderr, and **non-detached** execution;
- record the spawned wrapper (`cmd.exe`) PID at spawn, bound to the run token.

The observation window (`observation_window_seconds`, default 10) is fixed in the
harness or the run record and is not changed between repetitions.

## Procedure

1. Record the environment fields.
2. Launch the fixture through the Stage A harness. Record a **timestamp** before
   interrupting.
3. Wait for `AGENT-READY`.
4. Press **Ctrl+C** once. **Do not type any other key during the observation
   window.**
5. Observe for the fixed window, recording:
   - whether `AGENT-INTERRUPTED` appears and the finalization record is written;
   - whether `Terminate batch job (Y/N)?` appears;
   - whether the wrapper exits without any operator input.
6. Classify per the rules below.
7. Only **after** the window may the operator answer the prompt or invoke bounded
   cleanup. Record it as `operator_recovery_required: yes` — it does **not** change
   the original `wrapper_completion` classification.

## Classifying `interactive_delivery`

Classify `interactive_delivery: received` only when the token-bound finalization
record records the `SIGINT`-handler timestamp. Console text is corroborating
evidence, not the sole basis. Use `indeterminate` when output is visible but the
record is absent, malformed, or bound to a different token.

## Classifying `wrapper_completion`

- `clean_exit` — the wrapper closes without further operator input before the
  observation window expires, with no batch prompt observed.
- `batch_prompt_then_exit` — the prompt appears but the wrapper exits without
  operator input before the window expires.
- `batch_prompt_hang` — the prompt appears and the wrapper is still waiting at the
  end of the window.
- `wrapper_hang_without_prompt` — no prompt, and the wrapper is still alive at the
  end of the window.
- `indeterminate` — none of the above can be established.

## Exit evidence

Delivery and exit are established by records, not printed text alone:

- `agent_exit_observed` — the fixture's finalization record is present and
  `AGENT-INTERRUPTED` printed;
- `agent_exit_intent: 130` — the fixture's intended code;
- `wrapper_exit_code` — the `cmd.exe` process exit code as observed
  (`integer | null | unknown`). The wrapper's code may differ from the fixture's
  `130`; do not call it "verbatim" until proven.

## Terminal-host matrix

Ctrl+C behavior can vary by host. Test each configuration VibeRevert intends to
claim as supported. A configuration is the combination of terminal application,
hosting shell, and relevant versions. Suggested initial matrix entries:

- Windows Terminal + PowerShell
- Windows Terminal + Command Prompt
- classic conhost + Command Prompt
- VS Code integrated terminal + PowerShell

Support claims must remain scoped to configurations actually verified; untested
configurations remain unverified.

## Repeatability

A Stage A terminal-host configuration is eligible only after **three consecutive
runs** produce `received` + `clean_exit` with no surviving fixture process.

After H11.2 exists, its Stage B CLI regression must also pass **three consecutive
runs** for each configuration claimed as supported, with `end_session_ran: yes`,
`active_session_after: cleared`, a clean expected repository state, and no
surviving fixture process.

## Cleanup

In a `finally` path on every run:

- Identify fixture processes only by their recorded **PID plus token** — never by
  image name.
- Terminate any surviving fixture processes through the bounded cleanup harness.
- Verify that no fixture heartbeat continues advancing after cleanup. Treat the
  finalization record as immutable exit evidence, not a heartbeat.
- Preserve all evidence **before** deleting temporary files.
- Cleanup success is not proof that interactive completion succeeded.

## Evidence to retain

- [ ] Windows edition and build
- [ ] Terminal application, hosting shell and versions
- [ ] Node and agent-fixture versions
- [ ] Launch-plan strategy and harness identity
- [ ] Timestamp before Ctrl+C
- [ ] Ordered transcript or screenshot, with user paths redacted

- [ ] Wrapper completion and exit-code evidence
- [ ] Stage B session evidence, when applicable
- [ ] Surviving fixture-process count after cleanup

## Recorded results — 2026-08-04 (Decision 7: OPEN)

Two **separate** bodies of evidence. They are not merged into one verdict; the failed Stage A
evidence retains its meaning, and any future architecture requires a **new strategy identity**.

### 1. Stage A — `windows-cmd-bounded-v1` (formally ineligible)

The Stage A matrix ran on a real Windows console across all four required terminal-host
configurations, using source commit `811d463c0c147d2c129065158302000e71f9468b` and attestation
digest `ef1260dcbb1e3aa576ed63ccaf708077d6fb56af0fdc179cd0d8bb941267a466`. One qualifying
repetition was recorded per host. Each repetition produced the same blocking outcome. Three
consecutive eligible repetitions were required for the pass branch; because every case failed at
repetition 1 and no eligible sequence existed, repetitions 2 and 3 were unnecessary for the
present go/no-go decision. This does not establish that the failure is deterministic,
host-independent, or unreachable under every repetition.

| matrixCaseId | interactive_delivery | wrapper_completion (operator) | candidate_wrapper_completion (machine) | eligibility |
|---|---|---|---|---|
| `windows-terminal__powershell` | received | batch_prompt_hang | forced_recovery | blocked |
| `windows-terminal__cmd` | received | batch_prompt_hang | forced_recovery | blocked |
| `conhost__cmd` | received | batch_prompt_hang | forced_recovery | blocked |
| `vscode-integrated__powershell` | received | batch_prompt_hang | forced_recovery | blocked |

Ctrl+C reached the fixture in every case, but `cmd.exe` displayed `Terminate batch job (Y/N)?`
and hung until forced recovery — never `clean_exit`. Per the Eligibility rule, all four cases are
**blocked**; `windows-cmd-bounded-v1` remains **ineligible**. Evidence (external, uncommitted):
the operator evidence root (four sealed bundles) plus a `summarize-matrix.mjs --json` snapshot with
`matrixEligible: false`. This meaning is unchanged by anything below.

In the tested throwaway probes, the `& call set …=%%ERRORLEVEL%%` continuation suppressed the
prompt when a batch file directly launched a native executable. It did not suppress the prompt in
either tested `.cmd`-target topology: an outer wrapper calling the target `.cmd`, or a top-level
`/c` compound command calling the target `.cmd`. No tested continuation topology established viable
mediation of an existing `.cmd` target. This call-based continuation candidate is therefore not
being pursued further.

### 2. Native control-router feasibility spike (disposable; one host; NOT attested)

A distinct architecture — debug **only** `cmd.exe`, swallow its `DBG_CONTROL_C`, and leave native
descendants undebugged — was demonstrated by a **disposable, uncommitted** experiment. This is a
research record, **not** attested Stage A evidence and **not** product support.

- **Date / classification:** 2026-08-04 · Stage-1 feasibility demonstrated · one host · one
  representative launcher topology · one run.
- **Host:** Windows 10 Pro 10.0.19045 · Windows Terminal / PowerShell (Windows Terminal version
  not recorded · PowerShell version not recorded) · Node v24.13.1 (x64) · ComSpec
  `C:\WINDOWS\system32\cmd.exe`.
- **Topology:** `router.exe → cmd.exe [DEBUG_ONLY_THIS_PROCESS] → agent.cmd → node.exe`.
- **Compiler / command:**
  `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe /nologo /platform:x64 /out:C:\vr-decision7-diag\router.exe C:\vr-decision7-diag\router.cs`
  (csc v4.8.4084.0, C# 5).
- **Artifact digests (SHA-256; throwaway `C:\vr-decision7-diag\`, not committed):**
  - `router.cs`    `68e674ea7049d87ab6ebe22dec4c8030d61cdcd11e28ddd2d673782e1907b04a`
  - `router.exe`   `3c49e02d41e5a845672463fad3da883b2eafc13e78269d9bbc7d240d4fba41f7`
  - `agent.cmd`    `90be88b7b0c559e41d6d9d2e4544ce6183564799aea323c6e48d8ce9ef330a3a`
  - `child-v2.mjs` `f1d946f5687bdabf3d0d2c8b683f320d531ab6cde3b04262fb864ced29a2bdac`
- **Raw console transcript (operator user path redacted):**

  ```text
  PS <redacted>> C:\vr-decision7-diag\router.exe
  [router] topology=debug-only-cmd flags=DEBUG_ONLY_THIS_PROCESS
  [router] commandLine="C:\WINDOWS\system32\cmd.exe" /d /v:off /s /c ""C:\vr-decision7-diag\agent.cmd""
  [router] Press Ctrl+C once after AGENT-READY.
  [router] cmd.exe pid=31068 (debugged)
  AGENT-READY (pid 87400)
  Press Ctrl+C ONCE now.
  AGENT-INTERRUPTED
  [router] swallowed DBG_CONTROL_C for cmd.exe pid=31068
  [router] cmd.exe exit code: 130  (130=cooperative SIGINT; -1073741510=STATUS_CONTROL_C_EXIT)
  PS <redacted>>
  ```

- **Result:** `DBG_CONTROL_C` was handled specifically for the debugged `cmd.exe` (pid 31068); the
  native descendant (`node`, pid 87400) stayed undebugged and received the ordinary Ctrl+C
  (`AGENT-INTERRUPTED`); **no** batch prompt; the returning shell prompt shows autonomous return;
  `cmd.exe` propagated the cooperative exit `130`. The router created `cmd.exe` as its debuggee
  rather than attaching to an existing process; the experiment completed in the operator's
  interactive PowerShell session.
- **Not established here (deferred to post-beta):** the other three hosts; nonzero /
  `STATUS_CONTROL_C_EXIT` exit variants; multi-generation trees; children that opt out via
  `SetConsoleCtrlHandler(NULL, TRUE)`; the pure-batch limitation (no native descendant to
  interrupt); no-residual-attachment / no-lingering over many runs; arguments; and all
  productionization (native build, signing, AV/EDR reputation, Job-Object teardown) plus a formal
  attested matrix.

### Decision 7 status

**OPEN — core native-router feasibility proven on one representative launcher topology and one
host; pending post-beta productionization and formal validation.** Not closed; not passed. The
beta ships on the current contract (native direct-spawn; interactive `.cmd` gated; no
generic-`.cmd`-mediation claim). Any positive support decision requires a **new strategy identity**
(e.g. `windows-cmd-debug-router-v1`), security review, a compatibility matrix, and a formal
attested matrix — all post-beta.
